# Phase 3: legacy REST traversal and prospective protocol amendment

## Status and authorization boundary

This implementation is **not a new-run authorization**. No Phase 4 action is authorized. Production `main.ts` continues to omit the new `pagination` option: the default remains one legacy page per wallet poll with unchanged request parameters and cadence. Enabling additional pages changes acquisition opportunity, timing and request load materially; it requires an explicitly authorized prospective acquisition amendment before any new scientific run. Never enable it retroactively or mutate historical evidence. Cohort, 24-hour duration, REST source definitions, identity functions, source-first clocks, matching/comparator metrics, exclusions and scientific thresholds are unchanged.

2. [Get user activity](https://docs.polymarket.com/api-reference/core/get-user-activity) ([Markdown](https://docs.polymarket.com/api-reference/core/get-user-activity.md)): legacy `GET /activity`; limit default 100, maximum 500; offset default 0, maximum 5000, past-cap requests rejected with HTTP 400. Defaults are TIMESTAMP/DESC. Its `sortDirection` description explicitly says both orders are stable and pages compose without gaps/repeats for the same query at any limit/offset. However, default `end` is current time and there is no snapshot/version token or guarantee against later indexing of older records.

The v2 counterparts are explicitly mentioned by those documents but are **not used**. No offset semantics are inferred from v2. Time-window subdivision and new start/end/sort filters are also not used: these would need a separate acquisition amendment.

## Chosen traversal (disabled by default)

`RestPollerOpts.pagination = { maxPages, overlap }` is a deliberate code-level seam, not a new environment/CLI default. The supported opt-in traversal stays on the SAME legacy sources and original filters (`/trades` always `takerOnly=false`; `/activity` does not gain a TRADE-only filter). It adds only explicit offset:

- Start each wallet poll at offset 0. No persisted cross-poll watermark is invented.
- After a full page, propose `offset + limit - overlap`. Compare the complete preceding tail identity vector to the next page's prefix, in exact returned order.
- A mismatch, missing overlap (including unexpected empty page), oversized page, malformed item, HTTP/transport failure, publication failure, page budget or documented offset cap ends traversal. Already observed valid items retain their actual source-first arrival clocks; no page index/source timestamp backdates them.
- A short page with observed overlap is a stopping observation, **not completeness proof**. Even matched overlaps can hide records inserted outside the observed overlap between requests. Trade order is not documented; default-current-time activity queries are not immutable snapshots. Consequently every poll's coverage remains `UNKNOWN_UNPROVEN`, including uncapped/empty polls, and whole-run `restCompletenessUnproven` remains true. There is no “probably complete” branch or later-empty-page resolution.
- Each opted-in wallet poll has 1–16 requests, no retries inside that budget; overlap must be an integer in `[1, limit-1]`. Limits must be positive integers within the endpoint maxima. Offset never exceeds 10000 (trades) / 5000 (activity). The existing transport timeout is 15000 ms per request; maximum request timeout sum is 240000 ms per wallet poll (not a wall-clock guarantee for disk work). A five-wallet sweep can have at most 80 requests per source when configured at the maximum; production defaults remain five single-page requests per source/sweep.
- One page plus one bounded overlap vector is retained, not concatenated history. Identity membership uses the existing disk-backed exact publication index, not lifetime sets. Quarantine links per poll are bounded by the page budget. Transport JSON body storage is capped at 16 MiB; a larger body is cancelled and reported as malformed, never an empty success. Parsing and decoded objects add bounded constant multiples of that body budget. The transport body cap applies to the shared read-only REST helper (including metadata callers), not RPC.

## Append-only receipt and recovery contract

Each attempted page produces `REST_PAGE` plus a final `REST_POLL`, joined by a UUID `pollId`. Overlapping scheduled or direct wallet polls produce a `REST_POLL` with `SKIPPED`, null request metadata and `NOT_ATTEMPTED` publication. Page outcomes are `SUCCESS_EMPTY`, `SUCCESS_NONEMPTY`, `HTTP_FAILURE`, `TIMEOUT`, `PARSE_FAILURE`, or `PUBLICATION_FAILURE`. HTTP errors and nonarrays have `NOT_ATTEMPTED` publication, not empty publication success.

Pages record exact request URL/query params, offset/limit, request/response times, HTTP status and age/cache-control/etag/date; returned ordering explanation, first/last native identity/timestamp, SHA-256 of the returned-order identity vector, vector-complete flag, exact successful-new/seen/publication counts, quarantine IDs, overlap diagnostics, next offset (only if actually continuing), null cursor, and stop reason. A malformed vector has `identityVectorComplete=false`; its digest represents only the validated prefix, never a claimed full vector. Poll totals aggregate page counts (overlap repeats included); inherited vector metadata is explicitly scoped to LAST_PAGE_ONLY. Linked page receipts contain per-page vector hashes and first/last identity/timestamp metadata, **not full vectors**. New counts increment only after publication completes.

Scheduled multi-wallet sweeps isolate bounded malformed-page validation failures only after their quarantine, page receipt and final poll receipt succeed, and only while the operational sink and scientific store remain usable. Later wallets are then requested in the same cycle; the malformed wallet is retried normally next cycle. Direct `pollWallet` still rejects the validation error. Index preflight, invalid scientific stores, publication failures, broken sinks and unclassified exceptions abort the sweep and retire its timer; they are never reinterpreted as recoverable page failures. An aborted unsafe sweep does not manufacture SKIPPED receipts for unattempted wallets.

Quarantines carry `pollId`; receipts link quarantine IDs. An event publication failure uses the exact source-qualified raw reference `rest:<source>:<native identity>`. It resolves only after the existing store confirms that exact raw/source/reconciliation publication, including an exact identity encountered after restart repairs durable partial publication. Recovery does not clear HTTP, parse, cap, overlap, or unknown-coverage failures merely because another poll succeeds. Source-first clocks and existing FIRST winners survive recovery unchanged.

The operational index schema is advanced to 5 to force a safe cache rebuild. It streams authoritative receipts to rebuild whole-run page/poll/skip/failure/unstable/budget counts and retains constant-size UNKNOWN_UNPROVEN state. These counters participate in semantic digest validation; later short pages cannot erase earlier exhaustion. The production runtime snapshot exposes indexed `restCompleteness`. No tail or lifetime set is used as completeness authority.

Sink failure still latches the shared operational writer, stops all source controls, gates in-flight publication/continuation and prevents later requests. No recursive quarantine or fabricated final receipt is attempted after the sink breaks. A process crash before a page receipt can likewise leave an unreceipted request: this version does not claim crash-atomic complete-request accounting or snapshot completeness; the whole-run state is always UNKNOWN_UNPROVEN. A surviving page without its final poll is visible in indexed counts and immutable receipts. This limitation is not an authorization to proceed to Phase 4.

- `tests/rest-transport.test.ts`: malformed JSON preserves headers/status, bounded cancellation, normal payload preservation, body-read timeout.
- Existing Phase 1/2 publication recovery, all-source sink fault/control retirement, racing, bounded-memory, runtime-health and lifecycle suites remain required gates.

Operational diagnostics only; never use these counters to tune a scientific threshold or change the comparator. Honest `UNKNOWN_UNPROVEN` is acceptable instrumentation, not proof of complete coverage or launch readiness. Matched overlap alone is insufficient; no Phase 4 advancement is authorized.
