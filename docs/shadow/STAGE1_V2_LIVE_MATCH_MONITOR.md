`phase4.ts`, the lifecycle runner and legacy comparison CLI remain byte-identical.
The previous contract is preserved as PHASE4_COMPARISON_CONTRACT_V1_FROZEN.md.
The current contract governs stage1-v2 and is NOT approved for a scientific run
by merging this implementation. `npm run compare` now selects the approval-gated
v2 CLI; `compare:v1-history` is explicitly historical. Existing v1 artifacts keep
v1 meaning. No old output or evidence is rewritten.

V2 reuses v1's exact event matcher and prospective RAW/USABLE/decision formulas.
Unpaired events with unresolved counterpart coverage are INDETERMINATE, not proven
misses. Unknown REST pagination and skipped/throttled polls never prove absence.
Unresolved events are excluded from the resolved observed union and its whole-
population coverage percentages are null. Valid paired latencies stay comparable
when unrelated unpaired events are indeterminate. All upstream completeness remains
UNKNOWN_UNPROVEN, even after committed-ingestion capture closure.

Source event times before S are RETROSPECTIVE_RECOVERY; unknown origin and event
times after E are separately retained. They do not contribute prospective
coverage, latency or policy metrics. Evidence is neither deleted nor backdated.

## Existing status architecture and real evidence

The existing 60-second status publisher calls one bounded diagnostic worker;
the browser still refreshes status.json at its existing cadence. There is no new
server, provider polling, agent loop or trading control. If independent monitor
configuration is absent, the panel says COMPARISON_NOT_AUTHORIZED and shows no
counts. Explicit historical status views never reconcile live matches.

The operator installs `/var/lib/poly-shadow/stage1-monitor-config.json` only after
separate authorization. It contains runDirectory, pointerPath, authorityPath,
authorityPin, approvalPath and approvalPin. Each refresh checks the AUTHORIZED
current-run pointer, immutable run manifest/cohort/window/SHA, independently pinned
observational v5 authority, exact backend/bot installation enrollment and v2 approval.
Memory-validation paths/boundary markers, historical table exports and synthetic
capture authority are refused. No capture switch is changed or assumed enabled.

Input evidence is the authorized run's `shadow-data/source_observations.ndjson`
and `poly2-comparison-capture/source_fence.sqlite`, opened read-only. Signed commit
witnesses are checked with the existing production authentication implementation,
including chain/cursor continuity, admission/enrollment/epoch/retry identity, original
clock evidence and committed source IDs. The live prefix stops at validated CLOSE;
it does not claim to validate final ACK/fence/population/drain/archive closure.

Derived SQLite state lives under the publisher's existing private cache, outside
all runs. It indexes source identities, append offsets/boundary hashes, groups,
matching components, claims/results and materialized counts. Refreshes read only
new evidence. Modified/truncated boundaries, invalid signatures, clocks or identities
invalidate the projection; transient locks/read unavailability can retry on the
next existing publisher cycle. The cache is never scientific or capture authority.
Symlink/hardlink output paths are refused. No evidence is repaired or rewritten.

Confirmed counts include only MATCHED_HIGH_CONFIDENCE records from the unchanged
matcher, one Poly2 row to one Shadow economic group. Probable and ambiguous records
are separate. CHAIN + REST lanes in the same economic group count once. Late
competing candidates revoke provisional confirmations. Original source IDs, journal
byte offsets/sequence IDs and hashes link every confirmed row to both source records.
The table shows aliases, lanes, event/group identity, original first-seen clocks
and the unchanged signed time difference (Poly2 minus Shadow). The most recent pair
uses the later detection clock, with exact-instant ordering across timezone spellings.

## Bounds and visible limitations

Per refresh: at most 2MiB / 2000 rows per source, 128KiB per source frame, 64 dirty
components, 1024 source candidates/aliases per component, 12 recent displayed rows,
and 8 displayed Shadow trace references per row (truncation explicitly labeled).
Components merge neighboring canonical six-decimal size candidates when necessary;
this is candidate routing only, never a replacement matching heuristic.
Total source records/attempts are capped at 250,000 each. Derived main database is
capped at 65,536 pages (normally 256MiB), with a 512MiB additional file-size guard.
The worker has a 192MiB V8 heap ceiling, a 12-second parent timeout, and a 128KiB
output ceiling. No unbounded full-history scan occurs on dashboard refresh.

A high-volume matching component or oversized frame can exceed these diagnostic
bounds even when the underlying evidence is valid. MONITOR_RESOURCE_LIMIT or
MONITOR_UNAVAILABLE means counts are unknown, not that capture/science failed.
Acquisition continues independently; no automatic stopping/restarting occurs.
Backlog is REPLAYING, and all counts remain PROVISIONAL/not certified. Capture
missing/disabled/unavailable, stale acquisition/capture, unknown coverage, ended
window and revoked authorization are explicit states. Final scientific results
always require the separately validated sealed export and full evidence review.

## One-time early viability checkpoint

The normal live panel provides a current advisory viability diagnosis. A one-time
checkpoint is separately requested between 1800 and 3600 seconds after S:

```
npm run stage1:monitor -- <monitor-config> <same-private-projection-directory> \
  <actual-current-UTC> --checkpoint
```

The checkpoint is persisted once in private derived state with evaluatedUtc,
elapsed time, counts, source offsets and approval/authority pins; subsequent calls
return that same assessment, while current freshness remains separately visible.
Calling too early/late does not corrupt evidence or poison later refreshes.

- PAIRED_EVIDENCE_CONFIRMED: valid high-confidence prospective pairs, both systems
  fresh and replay/retention healthy.
- ACTIVE_NO_PAIRS_YET: both have prospective activity and usable identities but no
  unique high-confidence pairs. No observed eligible overlap is not a failure.
- CAPTURE_OR_IDENTITY_BLOCKED: authorization, enrollment or usable authenticated
  transaction identity is unavailable/incompatible.
- INSUFFICIENT_EVIDENCE: too early, empty eligible populations, stale inputs,
  unhealthy retention or incomplete replay. These are not automatic run controls.

No diagnostic can prove absent real market opportunities. It reports the absence
of observed overlapping eligible candidates, separately from known capture or
identity blockers. The checkpoint never certifies final scientific performance.
